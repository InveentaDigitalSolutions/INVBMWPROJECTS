Section 1

The situation before

The board loaded its data by pulling the entire ticket list into the app when the app started, then filtering and searching inside that copy. Two things followed from that, and the second one was the serious one.

  • The app was slow to become usable. Every start paid for every ticket, whether the user looked at one bucket or all six.
  • Tickets went missing from filters and search. The platform stops handing over rows at a fixed limit. Beyond it, the app simply did not have the ticket in memory — so a filter or a search that should have found it returned nothing, with no error and no warning. The board looked correct and was incomplete.
  • Bucket counts could not be trusted, because they were counted from the same truncated copy.

Why this matters more than speed. A slow board is visible and people work around it. A board that silently omits tickets is invisible, and the user has no way to tell a genuinely empty result from a truncated one. Completeness, not speed, drove the design of the rebuild.

Section 2

The approach

Instead of copying the list into the app and filtering there, the app now asks SharePoint a precise question and receives only the answer. The filtering, the searching and the counting all happen on the server.

The app asks, SharePoint answers

Every search, filter and tab change is translated into a single query and sent to SharePoint through a service call. The platform row limit no longer applies, because the app never asks for rows it will not show.

Load what is on screen

Each bucket loads its first 20 tickets, newest first. More are fetched only when the user asks for them. Opening the app costs 120 tickets in the active view, not the whole list.

Counts come from the source

The number next to each bucket is counted by SharePoint across the whole list under the same filter as the board — not from what happens to be loaded.

The two service calls run at the same time, so the board and its counts arrive together rather than one after the other.

Section 3

What was delivered

Grouped by what a user experiences. Everything listed here is live in the app.

Loading and completeness

  • Server-side loading for both the active and the history view, newest ticket first.
  • 20 tickets per bucket on open, so no bucket starts empty and no bucket dominates the initial load.
  • „Mehr laden" per bucket, adding 50 more each time, in the Kanban view and in the list view. Loading more in one bucket does not disturb the others.
  • A loaded / total counter on every bucket header, so a partly loaded bucket is visibly partly loaded.
  • Active and history are separate tabs, each with its own buckets, counts and paging state.

Search

  • Searches ticket name, IPQ-Umfangs-ID, Abteilung, Projektphase and Ticketgröße in one field.
  • Finds a word anywhere in the ticket name, not only at the beginning.
  • Accepts the ticket number, with or without the QMT-FL- prefix.
  • Handles apostrophes in search terms and filter values, which previously produced an error.
  • The search waits for the user to stop typing before querying, instead of firing on every keystroke.

  • Alle returns the tickets of the departments assigned to the user.
  • Externe Steuerung is scoped differently by design: Meine returns tickets assigned to the user, Alle returns the tickets of the user's Dienstleister.
  • The scope survives a language switch and a tab switch.

Views and language

  • Kanban / Liste toggle. The list view shows ID, Erstellt am, Projektphase, Abteilung, Enddatum, Lieferant and Komponente, and carries the same filters, search, counters and „Mehr laden" as the Kanban view.
  • Enddatum is the phase end date for ItO tickets and is empty for OtD.
  • Opening a ticket from either view opens the correct ticket, and opening a batch opens the whole batch.
  • DE / EN toggle on the board itself, not only on the start screen.

Correctness fixes

These are defects that were found and closed during the engagement. Several of them could write wrong data, which is why they were prioritised ahead of any remaining tuning.

  • Batch save. Saving a batch now fetches the batch from SharePoint at save time and updates every member — including members not visible under the current filter. Previously it worked from the loaded copy, so a filtered board could save an incomplete batch.
  • Batch delete. The same correction, plus a guard: a ticket with no BatchID is treated as a single ticket. Without that guard, deleting one legacy ticket without a BatchID would have deleted every loaded ticket without a BatchID.
  • A safety stop on batch operations above four tickets, matching the maximum batch size.
  • Bucket counts count tickets, not batches. The history totals now match the item count of the SharePoint list exactly. This was the mismatch reported from the business side.
  • Ticketgröße filter and search now match on the Ticketumfang value that is shown everywhere else in the app, so filter, search and form agree.
  • Six form dropdowns (Dienstleister, Komponente, Lead-Derivat, Folge-Derivat, Abteilung, Interessenvertretung) searched an internal system column and returned nothing when typed into. They now search the name.
  • Long source lists (Lieferanten, Checklisten, Interessenvertretung) were being cut off at the platform limit in the ticket form; they are now queried so that all entries are reachable.
  • Errors are shown. A failed query now produces a message instead of an empty board.

Platform hygiene

  • Seven SharePoint indexes added on the columns the board filters and sorts by, so the queries stay fast as the lists grow.
  • Both service calls run under the identity of the person using the app, so a user only ever receives what they are entitled to see.

Two observations shaped where the remaining effort went, and where it deliberately stopped.

  • The query itself is flat. Fetching 200, 500 or 2.000 tickets all completed in roughly the same time. The cost is the round trip, not the volume — so asking for more tickets is cheap, and asking more often is not.
  • About 1,25 seconds of every load is platform overhead for invoking the service call. Further tuning on the server side would not move it. The remainder scales with the number of tickets rendered, at roughly 11 ms per ticket.

Why 20 per bucket, and not fewer. Fewer tickets would load faster, but 20 already means a bucket can be showing less than it holds. Reducing it further was rejected: the engagement is about the board being complete, and the counter plus „Mehr laden" is what closes that gap honestly.

Section 5

Reading the board

Three things on screen mean something specific. They are worth knowing before testing, because two of them look like defects if read the wrong way.

The counter, for example 20/538

The left number is how many tickets of that bucket are currently loaded. The right number is how many exist in SharePoint under the current filter. They are meant to differ — that is the counter doing its job. „Mehr laden" raises the left number until the two meet, at which point the button disappears.

Batches in Ticket-Pool and In Vorbereitung

An ItO batch is several tickets that share one ticket number, one per phase. Each of those tickets appears as its own card, marked with the span of the batch — a three-phase batch shows three cards, each labelled T1-T3. Both halves of the counter count the same thing, so they agree. What changed in August is the total: a three-phase batch now contributes three to it, not one, which is why the numbers in these two buckets read higher than before.

History totals

A history bucket total is now exactly the item count you see in the SharePoint list under the same filter. If the two ever disagree, that is a defect and worth reporting.

Section 8

Known limits

None of these affect the board today. They are recorded so that whoever maintains the app recognises them if the data grows or the process changes.

  • Above 5.000 tickets in a single bucket, that bucket's total would be understated. The largest bucket is far below this today.
  • A seventh active status would not appear on the board. The list of statuses is defined in more than one place and would need to be extended in all of them.
  • The Benutzer list is at 387 entries. Above 500, one dropdown in the ticket form would begin to truncate and would need the same treatment as the other long lists.
  • Legacy ItO batches created before the batch counter existed fall back to counting the tickets currently loaded, so their phase label can understate under a filter. New batches are unaffected.
